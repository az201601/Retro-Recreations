# 01 — ROM 取证

> 对 `Chip 'n Dale - Rescue Rangers 2 (USA).nes` 的完整取证。工具：`tools/analyze_rom.py`，报告：`analysis/rom_forensics.md`。

| 项目 | 值 |
|---|---|
| 文件名 | `Chip 'n Dale - Rescue Rangers 2 (USA).nes` |
| 文件大小 | 262160 字节 = 16（头）+ 131072（PRG）+ 131072（CHR） |
| SHA256 | `34ca559b733ed910b0a493a0cb1f5d64e5cd9e7e4796032d986c08079573e047` |
| MD5 | `e78eb3226a9e09113be319fee1a84f4d` |

**校验结论**：CHR 与 NesCartDB 已知正版（RR2-M C CAPCOM / NES-DV-0 CHR）**完全一致**；

因此本文件是**可信正版转储**，后续所有“噪声”现象都是原版真实数据，不是转储损坏。

## 2. iNES 头解析

```
偏移  内容
00-03  "NES\x1A" 魔数 ✅
04     PRG ROM 大小：08 → 8 × 16KB = 128KB
05     CHR ROM 大小：10 → 16 × 8KB = 128KB
06     flags6 = $10 → bit0=0（头文件镜像位：水平）、bit4=1（Mapper 低 4 位 = 1）
07     flags7 = $00 → Mapper 高 4 位 = 0、非 NES2.0、非 VS、非 PlayChoice
08-0F  $00（保留）
Mapper = (flags7 & $F0) | (flags6 >> 4) = $01 → MMC1 ✅
```

> ⚠️ **镜像位陷阱**：flags6 bit0=0 写的是“水平”，但 MMC1 游戏的真实镜像由 MMC1 控制寄存器决定（本作 `$1E` = 垂直，见 §4）。
> 模拟器/工具若只看头文件会设错镜像。GMS 重制时直接用垂直镜像的 nametable 布局即可。

## 3. 中断向量与复位桩

PRG 末 6 字节（固定银行 `$FFFA–$FFFF`）：

```
NMI    = $C003
RESET  = $FFE0
IRQ    = $FFE0
```

`$FFE0` 复位桩（每个 16KB PRG 银行末 32 字节都重复此桩 + 向量，见 §5）：

```asm
$FFE0: SEI              ; 关中断
$FFE1: INC $FFE1        ; ★ MMC1 复位技巧：对 $FFE1 做读-改-写，写入 $E2（bit7=1）复位 MMC1 串行移位寄存器
$FFE4: CLD              ; 十进制模式清零
$FFE5: JMP $C000        ; 跳固定银行入口
$C000: JMP $C106        ; 主初始化
```

`INC $FFE1` 是 Capcom 经典手法：`$FFE1` 处字节为 `$E1`，INC 后写回 `$E2`，bit7=1 触发 MMC1 复位。
我们的反汇编器最初把它误标为“MMC1 写”，实为复位——已在 `docs/03` 纠正。

## 4. MMC1 控制字 `$1E`（关键纠正）

初始化在 `$C272`（见 `docs/03` §3）：`LDA #$1E` 后 5 次 `STA $9FFF`（LSR 串行，LSB 先行）。

MMC1 控制寄存器（`$8000–$9FFF`）位布局（以 NESdev / Nerdy Nights 为准）：

```
bit4: CHR 大小（0=8KB 整块，1=两个 4KB 独立）
bit3: PRG 大小（0=32KB 整块，1=16KB）
bit2: PRG 切换位置（0=切 $C000，1=切 $8000）
bit1-0: 镜像（0=单屏下，1=单屏上，2=垂直，3=水平）
```

`$1E = 00011110₂`：

| 位 | 值 | 含义 |
|---|---|---|
| bit1-0 | `10` = 2 | **垂直镜像** |
| bit2 | `1` | PRG 16KB 切到 `$8000–$BFFF`（低区） |
| bit3 | `1` | PRG 16KB（非 32KB） |
| bit4 | `1` | CHR 4KB×2 独立（`$0000` + `$1000`） |

> 早期误读为“32KB PRG”是把 bit3/bit4 与 CHR/PRG 顺序记反了。证据链：
> 游戏逻辑银行 6 在 `$8000` 以代码形态存在（`$8000: LDA $F0 / BMI / JSR $8200…`），
> 固定银行 7 在 `$C000` 以内核形态存在（NMI/复位），PRG 切换值 `$06/$03/$02/$04/$05` 均为 0–7 的 16KB 银行号。
> 若为 32KB 模式，`$06` 将越界且内核会被切走——不可能。故确认为 16KB 模式。

**MMC1 寄存器地址**（串行写，5 次）：

| 地址范围 | 寄存器 | 本作用途 |
|---|---|---|
| `$8000–$9FFF`（如 `$9FFF`） | 控制 | `$1E` |
| `$A000–$BFFF`（如 `$BFFF`） | CHR0（`$0000–$0FFF`） | `$C298` X 参数 |
| `$C000–$DFFF`（如 `$DFFF`） | CHR1（`$1000–$1FFF`） | `$C298` Y 参数 |
| `$E000–$FFFF`（如 `$EFFF`） | PRG（`$8000–$BFFF`） | `$C2C5` A 参数 |

## 5. PRG 银行（8×16KB）

| 银行 | 文件偏移 | 熵 | 代码率* | 性质（初步） |
|---|---|---|---|---|
| 0 | `$00010` | 6.655 | 56.8% | 数据：`00 F0 E0 D0…` 重复表 + 尾部 `$E0–$EF` 关卡数据 |
| 1 | `$04010` | 6.664 | 57.5% | 数据：图块地图？（`$1B–$47` 值域）尾部 `$FF` 填充 |
| 2 | `$08010` | 6.918 | 74.8% | 数据：关卡/CHR 银行表（`$BD84` 等，见 `docs/05`）尾部 `$FF` 填充 |
| 3 | `$0C010` | 7.337 | 64.9% | 数据：调色板表（`$B081`）、CHR 银行表、状态数据 尾部 `$FF` 填充 |
| 4 | `$10010` | 7.072 | 67.8% | 数据：指针表（`$80xx`）+ 数据 |
| 5 | `$14010` | 6.150 | 59.6% | 数据：指针跳表（`$8014/$809C/…`，疑音乐/实体脚本） |
| 6 | `$18010` | 6.550 | 70.9% | **代码**：游戏逻辑（`$8000` 入口，见 `docs/04`） |
| 7 | `$1C010` | 6.966 | 86.1% | **代码**：固定内核（`$C000`，见 `docs/03`） |

\* 代码率 = 线性扫描中合法 6502 操作码比例，仅作启发式参考（数据也可能偶然命中操作码）。

**银行尾部之谜**：银行 0–6 末 32 字节完全相同（复位桩 + 向量），银行 7 仅差 2 字节（`$0B` vs `$A4`、`$49` vs `$E2`）。
推测为 Capcom 链接器模板：每个银行独立链接时都带上复位桩/向量占位。仅银行 7 的桩/向量真实生效。

## 6. CHR 银行（32×4KB）

CHR 共 128KB = 32 个 4KB 子银行（MMC1 CHR0/CHR1 各选一个）。

| 范围 | 熵 | 图块 | 结论 |
|---|---|---|---|
| 0–14（60KB） | ~6.0 | 呈噪声（见 `docs/06`） | ⚠️ 开放问题：被用作精灵银行 12/14，但渲染为噪声 |
| 15–31（68KB） | ~5.1–6.4 | 清晰图形 | ✅ 背景、标题 Logo（30）、字体（31）、Chip（25）等 |

CHR 校验和已验证为正版，故噪声是**原版真实数据**，不是损坏。详见 `docs/06` §5 的假设与验证计划。

## 7. 字符串与文本

ASCII ≥6 字符共 1646 条，绝大多数是 CHR 图块数据的偶然命中（如 `p\`P@0 ` 重复），
**无明文 ASCII 对话**——文本使用字体银行 31 的图块索引编码（自定义字库），需按图块索引解码（阶段 C）。
